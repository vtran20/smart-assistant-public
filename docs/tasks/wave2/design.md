# Wave 2 coordination design

Implement the approved P04, P05 and P06 packages from baseline 04c8a5b. Codex remains the semantic coordinator/runtime. Standard-library Python helpers provide command responses, validated staging and existing deployment transactions; no model API, server, scheduler, accounts or P07–P09 workflow implementation.

## Contracts and ownership

| Package | Output | Exclusive ownership |
| --- | --- | --- |
| P04 | main(argv=None), JSON task/catalog/preflight commands, request-coordination skill | cli.py, __main__.py, test_cli.py, .agents/skills/request-coordination, examples/scenarios/coordinator, docs/tasks/p04, docs/evidence/p04 |
| P05 | validate_agent_definition(path), stage_agent(project_root, definition_path, record), manage-agent skill | agent_lifecycle.py, test_agent_lifecycle.py, .agents/skills/manage-agent, examples/agents, docs/tasks/p05, docs/evidence/p05 |
| P06 | validate_skill_definition(path), stage_skill(project_root, definition_path, record), manage-skill skill | skill_lifecycle.py, test_skill_lifecycle.py, .agents/skills/manage-skill, examples/skills, docs/tasks/p06, docs/evidence/p06 |

Root owns root configuration/guidance, canonical catalog, shared contracts, integration tests, serialized activation/probes and docs/evidence/wave2. No worker alters accepted P00–P03 files. Optional shared implementation changes require evidence and root coordination first. Workers use assigned .worktrees/p04–p06; tests use temporary roots, never live task state or native targets.

P04 command signatures/exit statuses follow the existing plan: JSON {ok,data,errors}; 0 success, 2 invalid input, 3 conflict, 4 unmet preflight/completion. TaskStore always receives completion_gate. Keep append-only previous cycles across updates; explicit failed resume uses P01.resume_failed and must be reachable through documented coordination. Task completion also requires no unresolved blockers. CLI does not infer account permissions, execute arbitrary commands or keyword-route specialists. The coordination skill gathers actual observed tools, runs catalog eligibility before delegation, scopes context, preserves user intent, records criteria/review/feedback/test bindings and interrupted next steps, and requires exact current selections without granting new permission. Built-in bootstrap coordination/management skills must remain usable to establish the catalog; catalog routing of additional capabilities still requires verified ACTIVE records.

P05/P06 stage only DRAFT records of their own kind, validate identity/path collisions and version immutability, hash complete private copies, return fresh validated records and never activate, mutate the catalog or invent validation/evaluation/native proof. Draft replacements of registered identity may preserve kind/target; unrelated same identity or native target collides. Public inputs normalize through P00 codecs. Staging stays outside native discovery and transaction storage, with symlink/special-file/resource escape checks. Native target manifest normalization must match P02, including agent target basename. Skill resource validation cannot mistake ordinary external documentation links for local traversal.

P05 default is inherited model/effort. A model/effort override cannot be enabled without an observed supported catalog; if unavailable the helper must precisely reject rather than use a guessed allowlist. Native agent schema requires name, description, developer_instructions; project cycle must apply to every staged definition. P06 minimal metadata format is documented explicitly; unsupported YAML metadata receives a precise unsupported result rather than silent misinterpretation. Skill bodies specify intended invocation scope, output/verification and the required project work cycle.

## Acceptance and delivery

1. Each package meets its approved API and behavioral criteria, meaningful RED/GREEN, independent review, recorded feedback and fresh final tests.
2. Combined CLI/helper tests verify persistent task creation/resume, no stale evidence completion, blockers/history enforcement, catalog eligibility/preflight boundaries, and staged agent/skill assets usable with DeploymentStore.
3. Installed-client evaluation separately observes coordination ordinary/ambiguous/unrelated/interrupted/missing-tool cases; synthetic researcher ordinary/out-of-scope/missing-tool plus disable/previous-version reactivation; synthetic skill direct/indirect/unrelated/incomplete/failed-tool plus disable/rollback in fresh sessions.
4. Every native observation binds deployed complete manifest/client/version/session/identity. No synthetic receipt is represented as actual discovery. Structural success alone leaves semantic/native acceptance incomplete.
5. Root integrates accepted candidates serially, runs combined checks, obtains independent integration review, resolves feedback and freshly tests identical product hashes before acceptance. Native deployment/catalog updates are serialized; isolated native probes do not touch live user tasks. Final root bootstrap skill activation is separately verified; additional demonstration assets stay isolated.
